---
extends:
when: Evaluating a repo's agent instructions (rule files, CLAUDE.md, AGENTS.md, generated rule sources), on "audit our rules", "do these rules work", "what are our rules missing", "do we still need these rules", or "dedupe our rules".
---

1. **Frame it.** Ask four questions of the instructions. Could an agent work this out from the repo and its tooling? Would it do the right thing without being told? Does the instruction still match the code? What do agents get wrong that no instruction covers? Any verdict is open: keep, reword, move into a tool, merge, delete or add. The evidence may favor more text, less text or no change. Before the first task runs, have the operator name the models that decide and the misses they forgive. With no operator to ask, use the models the team runs most, forgive nothing on them, and say so. Then write down what counts as a pass for a cell of one to three runs, and the result that would change each decision. A tie settles nothing: report it as inconclusive, apply no change from it, and list it apart from clear results. Throughout, use a script for anything counted, parsed or matched. When a decision LLM is available, a narrow model that answers one question with a calibrated confidence, use it for every yes-or-no or pick-one call, such as whether two instructions say the same thing. Keep general models for the agent runs and for reasoning across the results.
2. **Map what loads when.** For each harness the team uses, list every instruction surface with its load trigger (always, path glob, nested file, skill description, pointer from another file), its size, and what else reads it, such as review bots, lint messages, skills and docs. Prove loading by planting a codeword in each surface of a scratch copy, reading a file in its scope from a fresh session, and asking for the codeword. Name each harness you could not run as unproven. Note when a scoped rule arrives relative to the decision it governs, since it may load only once a matching file is touched.
3. **Check every claim is live.** Check each path, symbol, command, signature and count against the code. Compare each stated pattern with recent merged work as well as with the majority of the code, because the two can disagree in either direction. Record which claims lint, types or CI already enforce. Mine recent review comments and corrections for repeated mistakes, covered or not, as task material for step 6. Record only. Change nothing yet.
4. **Dedupe by load scope.** Find instructions stated more than once, within the repo and across any sibling repos you can read, and instructions that conflict. Two copies are duplicates only where their scopes overlap: a broader copy covers a narrower one, never the reverse. A copy a harness never loads covers nothing for that harness. Keep the copy with the broadest reach across the harnesses, and report copies in separate repos on their own, since they cannot cover each other without a shared source. Settle each conflict from step 3's evidence, or bring it to the operator. Do this with a rerunnable script that fails when an anchor stops matching, and treat the result as its own arm, because removing a copy or a pointer can change behavior.
5. **Build the arms.** Give every run its own clean checkout, all cut from one commit of the latest remote, outside the operator's checkouts and outside any folder with instruction files of its own. Arms are the current rules as control, a baseline with every file the harness loads as an instruction removed, and the deduped set. Keep code and docs in the baseline, and state whether skills stay and why. Regenerate per-harness copies in each arm. Remove generated copies by hand if the sync does not delete them. Keep dependencies readable so agents can inspect library types.
6. **Run real tasks.** Write prompts a teammate would type, in the vocabulary of the design and never of the rule, the helper or the check. Cover every instruction surface with at least one task, and add tasks from the repeated mistakes in step 3 whether or not an instruction covers them. Spend runs in stages, launched by a script, each with its own budget, and hold back enough for steps 10 and 11. Before the first stage, run one task to the end and confirm from its log that its edits and commands were not denied. First run each task once per arm on the cheapest deciding model. Then run a stronger deciding model only on tasks with a check that model could not settle. Then add runs, up to three per cell, only where a check is still mixed or arms disagree. Name what went unrun, because a check that looks settled after one run can still be noise. Run headless with project settings only, so user config, memory and unrelated connectors stay out. Give read-only access to any connector an instruction depends on. Scope write access to the checkout and cap spend per run. Confirm from each run's log that its working directory was its own arm, and throw out any that was not.
7. **Lock the rubric and calibrate the judge.** Write the rubric before reading any result, from the source code and team policy and never from the wording of the rule under test. Each check tests one thing with a mechanical pass condition, names the instruction it traces to or the gap it probes, and at least one check covers structure rather than vocabulary. A blinded judge sees a neutral label, never the arm or model, and quotes evidence for each grade. When a decision LLM is available, ask each check as its own question, and send low-confidence answers to a general model. Before trusting it, grade a seeded known-good and known-bad output and confirm both land correctly, on every judging model you use. When a check turns out flawed, report its score as written, declare the flaw, and apply any corrected check to every arm alike.
8. **Explain surprises before trusting scores.** Triage runs with no output, cells where every arm fails, cells where baseline beats control, and flips between arms. Name the cause from the logs: a missing connector, a prompt naming something that does not exist, a prompt that seeded its answer, a flawed check, a rule that never loaded, or a rule that misleads. Fix a harness or prompt flaw, then rerun that task across all arms. Read the judge's evidence on every failure and a sample of outputs per arm yourself, and say how much you read.
9. **Measure cost per session.** Record starting context, total context processed, turns, output tokens and cost per run, with the spread per task. Report the static size of the instructions next to the measured session cost, and name what limits the session cost from the run data. Size alone does not settle it in either direction.
10. **Decide per check, then test the wording.** Apply the decisions from step 1 to each instruction through the checks that trace to it. When a task exercises several instructions and the attribution matters, run an arm that changes only one. Baseline passes on the deciding models: the instruction is not needed for this behavior, on this sample. Control passes and baseline fails: it does work the repo cannot. Both fail with no instruction covering the behavior: a gap, so draft an instruction or a tool. Every arm fails despite an instruction: it is not working, so check the check, then try a tool or another wording, or accept the miss. Baseline beats control: the instruction misleads. Deduped falls below control: restore what the dedupe removed. For anything that stays or gets added, test wordings across the range, from abstract, which has less to go stale but may send agents exploring, to concrete, which spares the exploring but can rot. Keep the one that holds up best on quality, session cost and staleness together. Run each candidate as a new arm on the tasks its checks trace to. When verdicts collide, the deciding models' scores on that check win over the arm-level result. Label anything no task covered as untested, and leave policy, safety and compliance instructions to the operator.
11. **Confirm on fresh tasks.** Freeze the final text. Write new tasks with different wording and subjects, and adapt the rubric's checks to the new subject without changing what each one tests. Run them on the final text and the control, staged the same way. A loss here reopens step 10 for the instructions it traces to.
12. **Apply it.** Work in a fresh worktree from the latest remote. Apply the verdicts with a script and regenerate. Find every reference to a changed or removed instruction across bots, lint messages, skills, subagents and docs, and repoint each one. Run the repo's sync check if it has one. Name any line that changed after the final run as untested. Commit and open a PR only when asked.
13. **Report.** Open with the goal. Give the verdict per instruction with its evidence, pass rates per model and arm, session cost next to static size, what could break, what went untested, and the limits of the eval. When a diff is large, split its line count into hand-written and generated files. Measure overlap across repos before recommending shared content. With a PR, put a summary in its description and the full matrix in a comment. Remove scratch checkouts and worktrees, and keep the results and scripts.
